    \section{Part I: Cryptanalysis}

        \subsection{Ciphertext}

            The given ciphertext is a short English message written in a classical cipher:

            \begin{quote}
                \texttt{PRCSOFQX FP QDR AFOPQ CZSPR LA JFPALOQSKR.}\\
                \texttt{QDFP FP ZK LIU BROJZK MOLTROE.}
            \end{quote}

        \subsection{Letter frequency}

            Spaces and the period were ignored. There are 59 letters and 20 distinct symbols.
            Counts came from \texttt{code/frequency\_analysis.py}.

                    \bottomrule
                \end{tabular}
                \caption{Letter frequencies in the assigned ciphertext.}
                \label{tab:freq}

            The three most frequent ranks are \textbf{P} (7), then the tie \textbf{R, O, F} (6).
            In English, E, T, A, O, I, N, S, H, R are usually the most common letters, so P is a
            reasonable first guess for E or S.

        \subsection{Short English words}

            Two-letter English words that appear often include \texttt{OF}, \texttt{TO},
            \texttt{IN}, \texttt{IS}, \texttt{IT}, \texttt{AS}, and \texttt{AN}. Common
            three-letter words include \texttt{THE}, \texttt{AND}, \texttt{FOR}, and
            \texttt{ARE}.

            In the ciphertext, \texttt{FP} appears twice. \texttt{QDFP FP} is a four-letter
            word followed by that same pair, which matches the English pattern
            \textbf{THIS IS}. That single guess gives Q$\rightarrow$T, D$\rightarrow$H,
            F$\rightarrow$I, P$\rightarrow$S, so \texttt{FP} really is \texttt{IS}, and
            \texttt{QDR} becomes \texttt{TH?}, almost certainly \textbf{THE}
            (R$\rightarrow$E).

            Those mappings already show that this is \emph{not} a Caesar cipher: P maps to S
            (shift 11) while R maps to E (shift 13). It is a general monoalphabetic
            substitution.

                \item \texttt{CZSPR} $\rightarrow$ \texttt{C?USE} $\rightarrow$ \textbf{CAUSE}

        \subsection{Caesar brute-force program}

            Caesar has only 26 keys, so brute force is cheap. The program
            \path{code/caesar_bruteforce.py} does the following:

            \begin{enumerate}
                \item For every shift $0,\ldots,25$, decode each letter as
                    $(c - \text{shift}) \bmod 26$.
                \item Score the candidate with English letter-frequency chi-squared plus hits
                    against a small word list.
                \item Print all 26 candidates, best first.
            \end{enumerate}

            A true Caesar sample (the recovered proverb, shifted by 3) is recovered at
            shift~3:

            \begin{codeblock}{}{Best Caesar candidate on a known-shift sample}
ciphertext:
VHFXULWB LV WKH ILUVW FDXVH RI PLVIRUWXQH.

 1. shift= 3  chi2=   26.17  words= 7  <-- best
    SECURITY IS THE FIRST CAUSE OF MISFORTUNE.
            \end{codeblock}

            The same program on the \emph{homework} ciphertext never produces English. The
            ``best'' shift still reads as gibberish (\texttt{SUFVRITA IS TGU \ldots}). That is
            expected: the assigned text is a mixed substitution, not a constant shift.

            \begin{examplebox}[How to run it]
                \texttt{python3 code/caesar\_bruteforce.py 'YOUR CIPHERTEXT HERE'}
            \end{examplebox}

    \section{Part II: Kasiski examination}

        Vigen\`ere is a polyalphabetic substitution: a repeating keyword chooses a different
        Caesar shift for each position. Simple frequency counts on the whole ciphertext fail,
        because the same plaintext letter can encrypt to several ciphertext letters.

        Kasiski examination recovers the keyword length without guessing the keyword
        itself~\cite{kasiski-wiki}.

        \begin{enumerate}
            \item Scan the ciphertext for repeated strings of length at least three.
            \item Record the distances (in letters) between those repeats. Repeats usually
                occur when the same plaintext chunk lines up with the same keyword letters
                again, so the distance is a multiple of the keyword length $d$.
            \item Take the greatest common divisor of those distances. That GCD is a strong
                candidate for $d$ (or a small multiple of $d$).
            \item Split the ciphertext into $d$ independent Caesar streams: stream $i$ is
                every $d$-th letter starting at $i$.
            \item Attack each stream with ordinary frequency analysis, then reassemble.
        \end{enumerate}

        \begin{takeawaybox}
            Kasiski turns Vigen\`ere into ``find $d$, then crack $d$ Caesar ciphers.''
            The hard polyalphabetic problem collapses once the period is known.
        \end{takeawaybox}

    \section{Part III: Block-cipher modes on a bitmap}

        Electronic Code Book (ECB) encrypts each block with the same key and no chaining.
        NIST still documents ECB, but warns that identical plaintext blocks produce identical
        ciphertext blocks~\cite{nist-sp800-38a}. This section makes that warning visible.

        \subsection{Image conversion}

            Source file: \texttt{docs/images/source.jpg}. ImageMagick resized it to exactly
            $2000\times 2000$ and wrote a 1-bit binary PBM (Netpbm P4)~\cite{netpbm-wiki}:

            \begin{codeblock}{}{Convert to a 2000x2000 binary PBM}
magick docs/images/source.jpg \
    -resize 2000x2000! -colorspace Gray -threshold 50% \
    pbm:org.pbm
            \end{codeblock}

            The file header is two ASCII lines, then 500{,}000 bytes of pixels
            ($2000\times 2000$ bits, packed 8 per byte). That body length is a multiple of the
            AES block size (16 bytes), so \texttt{-nopad} is valid with no extra bytes.

        \subsection{Strip the header, encrypt, restore the header}

            Encrypting the header would destroy the PBM magic number, so only the pixel body
            is encrypted~\cite{openssl-enc}. Demonstration key and CBC IV (hex) are stored
            in \path{code/run_experiments.py}; they are lab constants, not production secrets.

            \begin{codeblock}{}{AES-256-ECB and AES-256-CBC on the pixel body}
openssl enc -aes-256-ecb -in org.x -out enc-ecb.x \
    -nosalt -nopad -K 001122...ccddeeff
openssl enc -aes-256-cbc -in org.x -out enc-cbc.x \
    -nosalt -nopad -K 001122...ccddeeff \
    -iv 0102030405060708090a0b0c0d0e0f10
            \end{codeblock}

            The original two-line header \texttt{P4} / \texttt{2000 2000} is prepended again
            so the results open as images.

        \subsection{Results}

            Figure~\ref{fig:modes} is left-to-right: original 1-bit image, AES-256-ECB, and
            AES-256-CBC.

            \begin{figure}[h]
                \centering
                \includegraphics[width=\textwidth]{images/mode-comparison.png}
                \caption{Original 1-bit image (left), AES-256-ECB (middle), AES-256-CBC (right).}
                \label{fig:modes}
            \end{figure}

            Larger individual frames are in \texttt{docs/images/}:
            \texttt{original.png}, \texttt{aes256-ecb.png}, and \texttt{aes256-cbc.png}.

        \subsection{What the pictures show}

            In ECB, repeated 16-byte plaintext regions (flat sky, dark hair, the dress) encrypt
            to the same ciphertext bytes. After the header is restored, those repeats still
            draw the outline of the figure. The middle panel is noisy, but the silhouette is
            still there.

            CBC XORs each plaintext block with the previous ciphertext block (the first block
            uses the IV). Equal plaintext blocks therefore become unequal ciphertext blocks.
            The right panel is unstructured static: no usable picture remains.

            \begin{takeawaybox}
                A block cipher is only as hiding as its \emph{mode}. ECB leaks repeated
                structure. Modes with an IV and chaining or feedback (CBC, CTR, GCM, \ldots)
                should be used for real data, especially images and other patterned files.
            \end{takeawaybox}

    \section{Part IV: Hashing, ciphers, and digital signatures}

        \subsection{Experimental design}

            Performance was measured with OpenSSL's own timing tool~\cite{openssl-speed}, not
            a stopwatch.

            \begin{itemize}
                \item Implementation: OpenSSL 3.6.4 (\texttt{/opt/homebrew/opt/openssl@3/bin/openssl}).
                \item Host: Apple M1 Pro, otherwise idle.
                \item Each algorithm ran for 3 seconds per buffer size, three independent times.
                    The table reports the \textbf{median} of those three runs.
                \item SHA-1 used the default provider. RC4 and Blowfish are legacy in OpenSSL~3,
                    so those two runs also loaded \texttt{-provider legacy}.
                \item DSA reports sign and verify rates at 1024-bit and 2048-bit parameters
                    (OpenSSL 3 no longer times 512-bit DSA).
            \end{itemize}

            \begin{codeblock}{}{Commands used for Part 4(a)}
openssl speed -seconds 3 sha1
openssl speed -seconds 3 -provider legacy -provider default rc4
openssl speed -seconds 3 -provider legacy -provider default blowfish
openssl speed -seconds 3 dsa
            \end{codeblock}

            OpenSSL prints symmetric throughput in thousands of bytes per second. Table
            values keep that unit.

            Fast is not the same as safe. RC4 won the throughput contest among the ciphers and
            still must not be used. DSA lost the throughput contest and is still the only
            primitive in this set that can bind a message to a private key.

        \subsection{Digital signatures}

            A digital signature does not encrypt the whole file with DSA. It combines a fast
            hash with a slow public-key operation:

            \begin{enumerate}
                \item The signer hashes the message (SHA family). The digest is short even if
                    the file is large.
                \item The signer applies the private key to that digest (DSA, RSA, or ECDSA).
                \item The verifier hashes the received message independently and checks the
                    signature with the public key.
            \end{enumerate}

            \begin{defbox}[What each piece contributes]
                \textbf{Hash:} cheap integrity check; any bit flip changes the digest.
                \textbf{Public-key sign:} only the private-key holder can produce a valid
                signature (authentication and non-repudiation).
                \textbf{Symmetric cipher (AES, historically RC4/Blowfish):} optional
                confidentiality for the payload, usually under a random session key.
            \end{defbox}

            The combination avoids each tool's weakness. DSA is too slow to encrypt megabytes.
            A hash alone is not a signature, because anyone can recompute it. A symmetric
            cipher keeps the bytes secret but does not prove who sent them. Real protocols
            therefore \emph{hash, sign the digest, and encrypt the body separately} (hybrid
            encryption plus signatures).

            For new designs, replace the lab primitives with SHA-256 (or SHA-3), AES-GCM or
            ChaCha20-Poly1305, and ECDSA/Ed25519 or RSA-PSS.
